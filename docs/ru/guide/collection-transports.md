# Транспорты сбора

То, каким способом данные хоста попадают в SKOPOS, — самое важное решение по
безопасности в этой установке, потому что оно определяет, что именно лежит у
SKOPOS в руках в момент, когда его взломают. Вариантов три.

| Транспорт | Что хранит SKOPOS | Что получит взломавший SKOPOS |
|---|---|---|
| `agent-push` *(рекомендуется)* | ничего | ничего на этом хосте |
| `agent-ssh` | ключ, умеющий два слова | один `ping`, один `collect` |
| `direct-ssh` *(legacy)* | ключ с полноценным шеллом | всё, что может эта учётка |

Задаётся на сервер в `servers.yaml` или в **Флот → сервер → Как данные этого
хоста попадают в SKOPOS?**

---

## agent-push — хост отчитывается сам

На хосте работает небольшой агент и сам отправляет собранное. SKOPOS никуда не
подключается и не хранит для хоста вообще никаких учётных данных, поэтому взлом
дашборда не даёт доступа к флоту. Это и есть весь аргумент — и причина, по
которой этот режим стоит по умолчанию.

```yaml
servers:
  - name: web-1
    source: ssh_nginx_access_log
    transport: agent-push
    address: web-1.example.com     # только метка для трафика, сюда никто не звонит
    nginx:
      access_log_path: /var/log/nginx/access.log
```

Подключение хоста:

```bash
python skoposctl.py node-ticket --server web-1
python skoposctl.py node-installer --server web-1 \
    --base-url https://skopos.example.com --out install-web-1.sh
```

Скопируйте установщик на хост и запустите — он сам спросит билет:

```bash
sudo bash install-web-1.sh
```

Он спрашивает, а не берёт билет аргументом, потому что всё содержимое `argv`
видно любому локальному пользователю в `/proc/<pid>/cmdline` и оседает в истории
шелла и в логе sudo — и это касается в том числе `printf` в конвейере
`printf ... | bash`. Для автоматических установок билет по-прежнему принимается
со stdin. Билет одноразовый и живёт 30 минут; долговременный секрет
выпускается на стороне сервера, возвращается один раз по TLS и сразу пишется в
файл с правами `0640`.

### Что ставится на хост

Два юнита, и разделены они намеренно:

- **`skopos-node-privdump.timer`** работает от root, **не принимает ни
  аргументов, ни ввода** и пишет вывод пробы в `/run/skopos-node/`. Всё, чему
  нужны привилегии, живёт здесь.
- **`skopos-node.timer`** работает от непривилегированного `skopos-node`, читает
  разрешённые каталоги логов и эти дампы, и отправляет их.

Разделение принципиально. Чтение `auth.log`, имена процессов в списке сокетов,
`fail2ban` и Docker требуют root или эквивалента. Выдать это отчитывающемуся
агенту — через группу `docker` или правило `sudo` — значит вернуть ровно ту
привилегию, ради устранения которой всё и затевалось: член группы `docker`
запускает контейнер с примонтированным `/`. Поэтому привилегированная половина
не принимает ввода вообще, а непривилегированная ничего у неё попросить не может.

Доступ к логам выдаётся ACL на указанные каталоги. Если файловая система не
умеет ACL, установщик откатывается на группу `adm` и громко об этом сообщает:
`adm` читает ещё и syslog, и всё остальное, что доступно этой группе.

Установщик **не создаёт правил sudo** и **не добавляет агента в группу docker**.
Нужны логи контейнеров — перечислите контейнеры явно; root-таймер прочитает
только их.

### Управление агентами

```bash
python skoposctl.py node-list                    # кто подключён, когда отчитывался, версия
python skoposctl.py node-revoke --key-id nk_...  # для выведенного из эксплуатации хоста
```

Задайте `SKOPOS_NODE_SECRET_KEY` — base64 от 32 случайных байт. Секреты нод это
HMAC-ключи, и SKOPOS обязан уметь их прочитать; с этой переменной они
запечатываются AES-GCM ключом, лежащим вне базы, так что утёкший дамп базы не
равен рабочим учёткам флота. Без неё секреты хранятся открыто, и `node-list`
об этом предупреждает.

```bash
python -c "import base64,os; print(base64.b64encode(os.urandom(32)).decode())"
```

## agent-ssh — для хостов без исходящего доступа

Тот же агент и тот же документ, но соединение открывает SKOPOS. Нужен, когда у
хоста нет пути наружу к дашборду.

```yaml
    transport: agent-ssh
    ssh:
      host: web-2.example.com
      user: skopos-node
      key_path: /root/.ssh/skopos-web-2   # свой ключ на хост, не общий
      mode: wrapper
```

Ключ прибит и в `authorized_keys`, и блоком `Match` в sshd:

```
command="/usr/local/bin/skopos-node ssh-op",restrict ssh-ed25519 AAAA...
```

Файл `authorized_keys` лежит в `/etc/ssh/authorized_keys.d/` и принадлежит root,
а не в домашнем каталоге агента, где сам агент мог бы его переписать и убрать
forced command. `ForceCommand` в sshd — второй рубеж: он старше всего, что
просят ключ и клиент, и ограничиваемая учётка изменить его не может.

По проводу идёт `v1 ping` или `v1 collect`. Больше ничего. Нет ни одной
операции, принимающей путь, имя контейнера или число, — значит, некуда
инъектировать и неоткуда выходить за allow-list: что хост готов читать,
определяет root-файл на самом хосте, а не вызывающая сторона.

## direct-ssh — старый путь

SKOPOS передаёт хосту шелл-скрипты, поэтому его ключ — это полноценный шелл.
Оставлен только для непереведённых хостов. Список даёт `skoposctl doctor`:

```bash
python skoposctl.py doctor
```

Если он сообщает, что один ключ открывает несколько хостов, — этот ключ стоит
вам их всех сразу. Если сообщает, что хост собирается от `root`, — этот ключ
представляет собой root-шелл, лежащий на машине со SKOPOS.

## Проверка ключей хостов

Оба SSH-транспорта проверяют ключи хостов по умолчанию. Запишите ключ один раз,
сверив отпечаток с самим хостом:

```bash
python skoposctl.py trust-host --host web-2.example.com --port 22
```

Хранилище доверия — `~/.skopos/known_hosts` (переопределяется через
`SKOPOS_KNOWN_HOSTS`). `SKOPOS_SSH_STRICT_HOST_KEYS=0` отключает проверку;
выигрыш — только непроверенное первое подключение, цена — тот, кто ответит по
этому адресу, получает весь поток логов и управляет каждым ответом.

## Чего всё это не решает

Стоит сказать прямо, потому что страница про безопасность, где перечислены одни
победы, — не страница про безопасность:

- **SKOPOS по-прежнему накапливает логи доступа всего флота.** Токены сессий в
  query-строках, ссылки на сброс пароля, полная история IP и user-agent
  посетителей ваших сайтов. Владеющий этой базой владеет и этим — независимо от
  того, каким транспортом всё пришло.
- **Скомпрометированный хост управляет тем, что он о себе сообщает.** Он может
  выглядеть здоровым, не будучи им. Снапшоты хранят, каким транспортом получены,
  и присланным доверия меньше, чем снятым независимо, — но это провенанс, а не
  доказательство.
- **HMAC симметричен.** Root на хосте — это возможность подписываться от его
  имени. Агент работает только на stdlib, а в стандартной библиотеке нет
  подписи с открытым ключом, которая бы это закрыла.
